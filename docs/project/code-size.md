# Code size

How big is ts-transformer, and how much of it is tests? This page answers
that with line counts per component, per crate or binding, and per language.
The tables are generated by `scripts/gen/loc-report.sh`; the surrounding
prose is hand-written.

## How to read the tables

Every **git-tracked** file with a recognised extension is counted, so the
`target/` tree, build outputs, and untracked local corpora never appear. The
vendored libsrt and librist submodules are counted in their own section at
the bottom and stay out of every ts-transformer total. Each line lands in
exactly one class:

| class | meaning |
|---|---|
| **code** | source that is not a comment or blank. For Markdown this is prose; for TOML / YAML it is configuration. |
| **test** | every line of a test file, **or** any line inside a Rust `#[cfg(test)]` item in a production file. This is the column that separates inline unit tests from the code they sit next to. |
| **doc** | documentation comments: Rust `///` and `//!`, Javadoc `/** */`, C `///`, Python docstrings. |
| **comment** | any other comment. |
| **blank** | whitespace only. |

A file is a *test file* when it lives under a `tests/`, `benches/`, or
`fuzz/` directory, under Java's `src/test/`, or is a Python `test_*.py`.
Markdown under those directories (fixture READMEs, movement maps) stays
prose. Inside a Rust test module, blank lines and comments are counted as
`test`, so the `test` column is the full footprint of the test code, not just
its executable lines. Note that the `tst-core` and `tst-pipeline` crates keep
most unit tests out of line under `src/<module>/tests/`, which the directory
rule picks up; the `#[cfg(test)]` rule is what catches the modules that stay
inline.

Comment detection is a line-oriented state machine, not a parser. It tracks
block comments and brace depth and ignores braces inside string literals and
comments, but a `/*` inside a string, or a raw string with embedded quotes,
can still misclassify a line or two. Treat the numbers as accurate to a
fraction of a percent, not to the line.

## Components

| component | what it contains |
|---|---|
| **tst-core** | MPEG-TS mux/demux, KLV, codec parsers, and the `Transport` / `RecvTransport` traits. Depends on nothing else in the workspace and is a standalone crate: a consumer that needs only parsing and muxing depends on it alone and never compiles `tst-pipeline`. |
| **tst-pipeline** | The sender/receiver shells and managed reconnect wrappers, layered on `tst-core`. Every transport crate and every binding depends on it, so it is only "compiled out" for a `tst-core`-only consumer. |
| **transports** | `tst-srt`, `tst-rtp`, `tst-udp`, `tst-tcp`, `tst-hls`, `tst-rist`: one crate per wire protocol, each listed on its own row with a group subtotal. Each depends on `tst-core` and `tst-pipeline`; none depends on another transport. |
| **sys** | `tstrans-srt-sys`, `tstrans-rist-sys`, `tstrans-mbedtls-src`: raw FFI bindings and build scripts over the vendored C libraries (the vendored trees themselves are not counted). |
| **bindings/c**, **bindings/python**, **bindings/jvm** | The C ABI (`tst-c` + `tst-c-core`), the PyO3 extension plus its Python package and stubs, and the JNI crate plus its Java sources. Each binding's own test suite is in its `test` column. |
| **examples** | The runnable Rust examples. C examples live under `bindings/c/examples` and are counted with the C binding. |
| **embedded** | The self-contained bare-metal and FreeRTOS reference projects under `embedded/`. |
| **test-infra** | `tst-test-helpers`, `tst-integration` (cross-binding harness), `tst-interop` (live tool matrix + soak), and the root `tests/` manifests and goldens. |
| **scripts** | `scripts/` (CI ratchets, generators, interop + release tooling), `embedded/scripts/`, and `oss-fuzz/`. |
| **ci** | GitHub Actions workflows. |
| **docs** | Every Markdown file in the tree, wherever it lives. |

The **vendored libraries** section counts the libsrt and librist submodules
at their pinned tags, source languages only (C, C++, headers, Python, shell;
upstream's Markdown and CI config are skipped), applying the same line
classes (their `test/` and `tests/` directories are the `test` column). The
numbers are the whole upstream repository, including apps, examples, and
build glue, not only the files that compile into `libtstrans`. In
particular, roughly four fifths of librist's lines are its `contrib/`
directory of bundled third-party code; librist proper (`src/`) is about a
tenth the size of libsrt's `srtcore/`. mbedTLS and the embedded RTOS
submodules (FreeRTOS kernel, FreeRTOS+POSIX, lwIP) are not counted.

## Regenerating

```bash
scripts/gen/loc-report.sh            # rewrite the tables above in place
scripts/gen/loc-report.sh --stdout   # print them instead
scripts/gen/loc-report.sh --json     # per-file counts for your own analysis
python3 -m unittest scripts/gen/test_loc_report.py   # the counter's own tests
```

Nothing in CI checks this page for staleness: line counts drift with every
PR, so a drift gate would only generate noise. Regenerate it when the numbers
matter, typically at a release or after a refactor arc, and commit the
result.
