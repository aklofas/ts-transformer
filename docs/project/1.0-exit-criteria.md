# 1.0 exit criteria

**Status: draft.** This page lists what must be true before the workspace
tags 1.0. It carries no date: 1.0 ships when every criterion below holds,
not on a calendar. Each criterion names the check that proves it, so a team
outside the project can confirm it from the repository and its CI runs
without asking anyone.

"Proved by" names a CI workflow, a script under `scripts/`, a file under
`tests/coverage/`, or a page section. "Today" says where the criterion
stands on `main` as this draft was written; it is context, not a promise.

## For the maintainer

These are choices the draft cannot make for you. Each changes what a
criterion below requires.

1. **Provisional modules under 1.0 semver.** Cargo's semver applies to a
   whole crate, so a Provisional module inside a 1.x crate cannot change
   incompatibly without a 2.0 unless the project says otherwise. Options:
   declare Provisional modules exempt from the crate's semver in
   [API stability](/docs/reference/api-stability.md); move them behind a
   non-default `unstable` cargo feature; or keep the wholly Provisional
   crates (`tst-hls`, `tst-rist`) on their own 0.x version line. The
   semver-checks criterion under "Rust API" depends on the answer.
2. **Mobile bindings and browser playback before 1.0.** Is the planned
   UniFFI binding (Swift and Kotlin) a 1.0 requirement, or may 1.0 ship with
   the Rust, C, Python and JVM surfaces only? The same question applies to
   the planned WebRTC playback surface. The `tst-pipeline::binding` row's
   "Before Stable" clause assumes the mobile bindings come first.
3. **`DemuxFromFile`.** It has been deprecated since 0.6.0 with "removal no
   earlier than 1.0". Remove it before 1.0, or carry it, deprecated, through
   the whole 1.x line?
4. **Which tree the 72-hour soak must run on.** The 1.0 candidate itself,
   or any earlier tree when nothing on the soaked paths changed since?
5. **The CI flake ledger.** Known CI flake classes are kept outside the
   repository today. "Acceptable open findings" asks for each to be listed
   with its ledger entry; decide where the published copy lives.
6. **The C column of the surface manifest.** `tests/coverage/surface-manifest.toml`
   still has C cells marked unclassified, frozen in count by its rail.
   Must that count reach zero before 1.0, or may 1.0 ship with the C
   surface narrower than Rust's, as documented?
7. **Severity.** "No open correctness finding of high severity" needs a
   scale and an issue label. The draft's working definition is in that
   section; confirm it or replace it.

## 1. Surfaces

Every module is classified in the module table of
[API stability](/docs/reference/api-stability.md). That table is the
source of truth; this section only says which rows 1.0 needs.

**Must be Stable at 1.0.** Every row that is Stable today stays Stable. The
rows the project's scope rests on are named here so a reader can check
them first:

| Surface | Rows in the module table |
|---|---|
| MPEG-TS mux and demux | `tst-core` `mpegts`, `io_file`, `shared` |
| KLV substrate and MISB ST 0601 | `tst-core` `klv`, its machinery rows, `klv::st0601` |
| Primary video codecs | `tst-core` `codec`, `codec::util`, `codec::h264`, `codec::h265` |
| Transport contract and errors | `tst-core` `transport`, `error`, `cancel`, `net`, `url` |
| SRT | `tst-srt` `(crate)` |
| The pipeline shells and reconnect | `tst-pipeline` `mux_sender`, `sender`, `raw_sender`, `demux_receiver`, `receiver`, `raw_receiver`, `managed_demux_receiver`, `managed_receive`, `reconnect`, `shell_error` |
| UDP, TCP, RTP | `tst-udp` `(crate)`, `tst-tcp` `(crate)`, the Stable `tst-rtp` rows |
| The C ABI | `tstrans.h` under the rules in section 3 |

**May stay Provisional at 1.0.** The newer codecs (`codec::h266`,
`codec::av1`) and audio parsers; the typed KLV sets other than ST 0601;
`tst-hls` and `publisher`; the RTSP server and its publisher role
(`tst-rtp` `rtsp`); `tst-rist`; the binding handle layer
(`tst-pipeline::binding`) and the URL openers and shells the bindings use.
Each Provisional row says what would let it move in its "Before Stable"
column.

| Criterion | Proved by |
|---|---|
| Every public module has exactly one row, and every row names a real module | `scripts/check/rust/api-stability-coverage.sh`, run by the ratchets sweep in `ci.yml` |
| Every Provisional row has a "Before Stable" clause | the same table; a row without one is a gap in this document |
| No row is Experimental | the module table |

|---|---|---|

From 1.0, a breaking change to a Stable item needs a deprecation cycle of at
least one minor release and a major version, as the "Tiers" section of
[API stability](/docs/reference/api-stability.md) states.

## 3. C ABI

The rules are the ones the "Versioning" section of the
[binding-authors guide](/docs/reference/binding-authors.md#versioning)
states: `TST_ABI_VERSION_MAJOR` moves on an incompatible change,
`TST_ABI_VERSION_MINOR` on an additive one, `TST_ABI_VERSION_PATCH` on a
fix that keeps shape and behaviour. Three checks enforce them, in the order
a change meets them:

| Check | Where it runs | What it refuses |
|---|---|---|
| The stale-header refusal | every CI build of `tst-c` | a regenerated `tstrans.h` that differs from the committed `bindings/c/include/tstrans.h` |
| `scripts/check/c/abi-symbols.sh` | the `build` job in `ci.yml` | an exported name not in `bindings/c/abi-symbols.txt`; a name present at the previous tag and gone now; a name added without a higher minor |
| `scripts/check/c/abi-compat.sh` | the `c-abi` job in `ci.yml` and the qualification run | an `abidiff` change against the previous tag's library: a removed or changed function, a struct that grew or moved, a renumbered enumerator, an addition without a minor bump |

**At the 1.0 bump:**

| Criterion | Proved by |
|---|---|
| `TST_ABI_VERSION_MAJOR` becomes 1 | the constant in `bindings/c/core/src/lib.rs` and the committed header; `scripts/check/repo/release-version-consistency.sh` |
| The `c-abi` job passes the previous and current majors to `abi-compat.sh`, the way it passes the minors today | the `c-abi` job in `ci.yml` (its comment marks this as a 1.0 item); without it, the intended break fails the job |
| `abi-symbols.sh` accepts the removals the 1.0 major makes | the script; today a removed name fails whatever the major, by design before 1.0 |
| Every struct added from 1.0 starts with a size field | the struct definitions in `tstrans.h`; the "How these rules are checked" section of the binding-authors guide states the rule |
| The existing stats structs convert to the size-field shape once, at the 1.0 major | the 1.0 header against the last 0.x header in the `abi-compat.sh` report of the qualification run |
| `bindings/c/abi-symbols.txt` becomes the input of the distribution's symbols file | the distribution packaging reads it; no hand-written symbol list exists beside it |
| The 1.0 candidate's qualification record shows the C ABI leg compatible | the `abi.json` entry of the record (verdict `compatible`) |

## 4. Evidence

| Criterion | Proved by | Today |
|---|---|---|
| A **GO** qualification record on the exact 1.0 candidate commit | the `release-qualify.yml` run on that commit, committed as `docs/project/qualification.json` and rendered on the [validation evidence](/docs/project/validation-evidence.md) page. `scripts/gen/qualification.py` writes GO only when every required leg (interop, the four sanitizer jobs, fuzz, the JVM jar, the Python wheels, the C ABI, `ci` on that commit) concluded `success`, the tree was clean, the fuzz leg ran every declared target with no crash, and the interop census was full | the pipeline exists; the procedure is in [Releasing](/docs/project/releasing.md) |
| A 72-hour soak whose harness verdict is PASS | a `kind = "soak"` entry in `tests/coverage/evidence-archives.toml` with `overall_pass = true` on the agreed tree, its archive cited on the evidence page | **not met.** See below |
| An interop census with zero unexpected failures | the interop entry of the GO record: shape `full`, total equal to the census declared in `scripts/interop/expectations.toml`, and `fail`, `skipped` and `stale` all 0. Every failure the matrix accepts has a row in `expectations.toml` backed by a run that reproduced it | the latest full census had zero unexpected failures |
| The maintainer-local checks were run on the candidate and their results noted | the record's `maintainer_local` list: the real-capture corpus cross-check, long fuzz runs, the benchmark regression check, the one-hour synthetic soak | done by hand at each tag, per [Releasing](/docs/project/releasing.md) |

**The 72-hour soak today.** The latest 72-hour SRT and RIST run is the 0.7.0
release soak (2026-10-01 to 2026-10-04). Its harness verdict is
`overall_pass=false`, and it does not count as a PASS. The SRT leg passed
every gating verdict. The RIST leg failed corruption attribution: the
harness could not explain eight corruption events, and all eight were
traced to two defects in the harness's own attribution, fixed in 0.8.0,
not to the library. That explanation is why the failure is not a library
defect; it does not turn the run into a pass. The verdict the harness
printed is the verdict that counts, and a fresh 72-hour run must print
PASS. The only 72-hour run with an overall PASS (2026-08-05) predates the
corruption tap and the current soak shape and did not record its source
commit, so it does not satisfy this criterion either.

**Open evidence gaps.** Each is a missing proof, not a known defect. Each
must be closed, or accepted by the maintainer as a limitation stated in the
1.0 release notes.

| Gap | What is missing | Status |
|---|---|---|
| KLV timing oracle for elementary RTSP publishing | No interop check relates a KLV unit's PTS to the video PTS the server placed it against when a publisher sends H.264 and KLV as separate RTP tracks. The interop cell proves KLV content only; placement is pinned by the aligner's unit tests alone | open |
| Elementary H.264 + KLV soak leg | The soak's `rtsp-publish` leg is MPEG-TS passthrough and never reaches the re-muxer, so the elementary path (RTP H.264 and RTP KLV through the publisher, aligner and re-muxer) has no long-duration run | open |
| ARM64 interop subset | The interop matrix and the soak run on linux-x86_64 only. linux-aarch64 is a gating CI platform for the build and tests, but no interop cell has run on it | open; see section 5 |

## 6. Acceptable open findings

1.0 may ship with open issues, under these limits:

| Criterion | Proved by |
|---|---|
| No open correctness finding of high severity | the issue tracker. Working definition of high severity until the maintainer sets one: wrong bytes on the wire or in a decoded record, data lost without a counter or an error saying so, a crash or hang in library code, or memory unsafety. Security reports follow [SECURITY.md](/SECURITY.md) |
| Every known flake is listed with its ledger entry | interop flakes are the `known_flaky` rows in `scripts/interop/expectations.toml`; timing-sensitive skipped tests are the `environmental` entries in `tests/coverage/skip-ledger.toml`; CI flake rates are the latest row of [`docs/project/ci-health.csv`](/docs/project/ci-health.csv), written by `scripts/dev/ci-health.sh`. The 1.0 release notes list each with its entry |
| No test is disabled for a bug | `tests/coverage/skip-ledger.toml` has no active `blocked_bug` entry; checked by `scripts/check/repo/skip-ledger-sync.sh` |
| Every documented deferral was read again and confirmed once before 1.0 | each entry in [deferred features](/docs/project/deferred-features.md) still holds its "Why deferred" and "Trigger to revisit"; an entry whose trigger has fired is either built or restated as post-1.0 |
